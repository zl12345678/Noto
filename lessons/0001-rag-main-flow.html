用 Java 后端思维讲清 Noto 的 AI 问答

这节课假设你会 Spring Boot、Controller、Service、数据库和日志，但没做过 AI。学完后，你要能应对本项目 AI 问答追问，并知道如何自己开发一个小 AI 模块。

先把 AI 当成一种后端能力

不要先把 AI 想复杂。在这个项目里，AI 模块本质上还是后端调用链：Controller 收请求，Service 组织上下文，调用外部模型服务，解析返回，写审计日志，再把结果给前端。

必须先懂的 10 个词

LLM

大语言模型。你可以先理解成“输入文本、输出文本”的远程智能服务。Noto 用的是 DashScope 的 Qwen。

Prompt

发给模型的完整指令，不只是用户问题，还包括角色、规则、检索资料、输出格式要求。

Token

模型处理文本的单位，近似理解成字或词片段。流式回答时，前端一段段收到的就是 token 片段。

Embedding

把一句话或一段文本变成一组数字，像给文本做“语义指纹”。

Vector

Embedding 生成的数字数组。项目里是 float[]，会保存到 note_rag_chunk。

Vector Search

按语义相似度找文本，不是简单 like。比如“上线注意事项”能找出“部署风险”。

RAG

Retrieval-Augmented Generation：先检索资料，再让模型基于资料回答。它是减少胡编的核心手段。

SSE

Server-Sent Events。后端不断向浏览器推送文本片段，所以用户看到答案逐字出现。

Agent

让模型规划业务动作，比如“搜索文档 -> 提取待办 -> 创建提醒”。写操作需要用户确认。

Hallucination

模型编造。Noto 用检索引用、知识缺口、确认链和审计来降低风险。

更多术语可复习：Java 开发者 AI 术语速查。

本项目 AI 问答做了什么

用户问“这个知识库里关于项目部署有哪些注意事项？”时，Noto 不是直接把问题丢给模型。它做了这 6 步：

1. 接收请求

AiController.askStream 接收问题、workspaceId、scope、sessionId。

2. 补全上下文

buildAskContext 合并用户问题、会话历史和用户偏好。

3. 检索笔记

NoteRetrievalService 先向量检索，再用关键词检索补强。

4. 组装 Prompt

把检索片段、回答规则、知识缺口指令和当前问题拼成完整 prompt。

5. 调模型

StreamingChatModel 调 Qwen，边生成边返回。

6. 返回与审计

SSE 发 references/token/done，并记录 audit log 和会话消息。

RAG 用 Java 话怎么理解

RAG 可以理解成一个“先查库再调用模型”的后端模式。

// 伪代码：不是项目原代码，但很像这个项目的结构
public AiAnswer ask(String question, Long workspaceId, Long userId) {
    List<Chunk> chunks = retrievalService.retrieveForQuestion(userId, workspaceId, question);
    String prompt = promptBuilder.build(question, chunks);
    String answer = chatModel.chat(prompt);
    auditLogService.logAiCall(userId, workspaceId, prompt, answer);
    return new AiAnswer(answer, toReferences(chunks));
}

所以你面试时不要只说“我接了大模型 API”。要说清楚：模型回答前，我先把用户私有知识查出来，作为证据交给模型。

索引链路：笔记怎样变成可检索资料

RAG 查询能工作，前提是笔记已经提前处理过。这个处理过程叫索引。

步骤人话代码入口
分块 把长笔记切成小段，避免一次塞太多内容给模型。 NoteChunkSplitter.split
生成 embedding 把每个文本片段转成数字向量。 embeddingModel.embedAll
保存 chunk 把文本片段、位置、模型名、向量写入表。 note_rag_chunkMapper.insert
写入 pgvector 如果数据库支持向量列，就额外写入 embedding_vector。 PgVectorSupport.storeEmbeddingVector

查询链路：问题怎样找到相关笔记

用户的问题也会被转成向量，然后和笔记片段向量比较。相似度越高，越可能被放进 prompt。

项目里还有两个工程细节很值得讲：

细节为什么重要
关键词补强 Embedding 适合语义，但有时专有名词、标题关键词更准，所以项目把关键词结果合并进去。
Fallback pgvector 不可用时不直接挂掉，而是退回 Java 内存 cosine 扫描，保证演示和开发环境可用。

如何自己开发一个小 AI 模块

如果你要在这个项目里加一个“AI 生成笔记标题”模块，不要一上来做 Agent。按后端最小闭环做：

  1. 定接口：新增 POST /api/v1/ai/notes/{id}/suggest-title。
  2. 拿数据：用 noteService.requireOwnedNote 读取当前用户的笔记。
  3. 写 prompt：告诉模型只输出 JSON，例如 {"title":"..."}。
  4. 调模型：复用 ChatModel 或 AiServiceImpl.callModel 的模式。
  5. 解析结果：用 ObjectMapper 读 JSON，失败时给可控 fallback。
  6. 写审计：记录 actionType，例如 ai.suggest_title。
  7. 前端确认：只返回建议标题，不直接改笔记；用户点确认后再保存。

你真正要掌握的是这个套路：业务数据 -> prompt -> 模型 -> 解析 -> fallback -> 审计 -> 用户确认。

面试回答模板

如果面试官问“你这个 AI 问答怎么实现的”，你可以答：

我把它当成一个后端检索增强问答链路来做，而不是直接调用聊天 API。
用户提问后，Controller 进入 AiService，服务层会先根据 workspace 和 scope 检索用户自己的笔记。检索分两层：优先用 embedding + pgvector 做语义召回，pgvector 不可用时退回 Java 内存 cosine；同时合并关键词结果，避免专有名词漏召回。
拿到片段后，我把片段、引用、会话历史、用户偏好和“资料不足不要编造”的规则拼成 prompt，再通过 LangChain4j 调 Qwen。流式接口用 SseEmitter 先返回 references，再逐 token 返回答案。
最后会保存会话，并记录 AI 调用审计，包括模型、耗时、prompt 预览、响应长度和错误。这样面试里我可以讲清楚检索、生成、流式、引用和工程兜底，而不是只说接了大模型。
